# FixMyCar reference (moved out of CLAUDE.md)

Detailed architecture notes for Quote My Garage, moved out of `CLAUDE.md` so they are not loaded into every session. Nothing here was rewritten: the sections below are the original text. `CLAUDE.md` keeps the commands, the test rules and a short list of the invariants that must never be broken; read the matching section here before changing that area.

## Architecture

### Local DB is SQLite; production is Postgres

`prisma/schema.prisma` hardcodes `provider = "sqlite"` for local dev (`prisma/dev.db`, gitignored). `.env.example` and `AWS-DEPLOYMENT.md`, however, configure `DATABASE_URL` for AWS RDS **PostgreSQL**. Because SQLite has no native array/JSON type, list-like Garage fields (`services`, `images`) and `openingHours` are stored as JSON-encoded strings and parsed at the application layer via `src/lib/garage-mapper.ts` (`parseServiceList`, `parseImageList`, `parseOpeningHours`). If ever deploying against real Postgres, the schema provider needs to be switched deliberately — don't assume the two are interchangeable as-is.

### Four roles, enforced at the proxy layer

`User.role` is one of `OWNER | GARAGE | ADMIN | SUPER_ADMIN` (a plain string; `src/lib/roles.ts` has `isAdmin()` = ADMIN or SUPER_ADMIN, and `isSuperAdmin()`). **Never write `role === "ADMIN"` in an admin route: use `isAdmin()`**, or a super admin is locked out. SUPER_ADMIN is a strict superset of ADMIN and additionally owns: `/admin/settings` (platform credentials), inviting garages, and granting/removing admin roles. Ordinary admins can't touch admin-level accounts (`touchesAdminAccount()` in `app/api/admin/users/route.ts`), and nobody can change, suspend or delete their own account, which also means the last super admin can't be removed. The admin layout picks the `superAdmin` portal nav (adds a "Platform" section); the page and API each re-check the role, since hiding a link isn't protection. The first super admin is promoted by SQL (see `VERCEL-DEPLOYMENT.md`).

Garages are separate businesses with their own owner and login; the super admin onboards them (`POST /api/admin/garages/invite`: a PENDING garage + a password-less owner who gets a 7-day set-password link, reusing `/reset-password`; `src/lib/garage-invite.ts`) but does **not** edit their prices or details (`GET /api/admin/garages/[id]/pricing` is read-only, shared `loadPricing()` in `src/lib/portal/pricing-read.ts`).

`proxy.ts` (the Next 16 name for middleware) uses `withAuth` (NextAuth) to gate `/dashboard/*` (OWNER), `/garage-dashboard/*` (GARAGE), and `/admin/*` (ADMIN) by checking `token.role`, redirecting to `/login?error=unauthorized` on mismatch. API routes re-check `session.user.role` themselves (see `app/api/job-requests/route.ts` GET handler) — the proxy does no authorisation on `/api/*` (it only refuses cross-site writes there, see CSRF below), so any new API route touching role-restricted data must do its own `getServerSession(authOptions)` + role check.

Auth config lives in `src/lib/auth.ts`: JWT session strategy, Google OAuth + credentials (bcrypt-hashed password) providers, `PrismaAdapter`. Role and user id are threaded through via the `jwt`/`session` callbacks onto `token`/`session.user` (typed in `src/types/next-auth.d.ts`). **A revoked token (suspended/deleted user, "sign out everywhere", password change) yields NO session at all** (the session callback returns `{}`, so `getServerSession()` is `null` and every `if (!session)` guard rejects it). It used to return a session with `id`/`role` undefined, and Prisma silently drops an `undefined` filter, so `where: { userId: user.id }` matched every user's rows. Use `requireSession()` (`src/lib/session.ts`) where a user id goes into a query. Changing or resetting a password bumps `User.sessionVersion`, which signs out every session. Sign-in checks the password before saying anything about suspension or lockout and always runs bcrypt (no account enumeration by message or timing).

### Garage businesses, locations, staff and permissions (`src/lib/org/*`)

A garage is a **business** (`Organisation`) with one or more **locations** (`Garage` rows; every child table still keys on `garageId`). People belong to a business through `Membership`, and hold **roles at locations** through `RoleAssignment` (`scopeKey` = a garage id, or `"*"` for all locations including future ones). `User.role` stays `GARAGE` for every staff login, so the proxy and role helpers are unchanged. A garage with `organisationId = null` (not yet backfilled) still works through the legacy path: its login is the owner.

- **Permissions** are a code catalogue (`permissions.ts`; location-scope and organisation-scope keys, with `implies`). A `Role` row stores a JSON snapshot; the system roles (Owner, Manager, Staff) are created with the business and presets (`presets.ts`) ship disabled and are copied in when enabled. **Organisation-scope keys (billing, roles, locations, website, business details, audit) only count from a role held at ALL locations**; Owner always has everything (`access.ts`, pure and exhaustively tested).
- **One resolver decides everything**: `resolveGarageAccess()` (`resolve.ts`) turns a user into business + active location + effective permissions. The active location is requested via the `x-qmg-location` header or `qmg_loc` cookie, is never in the JWT, and is only ever a *request* checked against assignments (a foreign or junk id falls back to the default). Never write `prisma.garage.findUnique({ where: { userId } })` in a route: `src/lib/org/architecture.test.ts` fails the build if you do.
- **`withGarage(label, handler, { permission, write? })` requires `permission`** (a key, `{ anyOf: [...] }`, or `"member"`); the type forces it and the architecture test holds a reviewed snapshot of every route's permission, so loosening one is a visible diff. Inside a handler use `ctx.can("key")` for checks that depend on the request (CSV exports need `bookings.export` / `customers.export` on top of `.view`) and `forbidden()` for the 403. Routes shared with customers (`bookings`, `quotes`, `messages`, `job-requests`, `garages/[id]`, `upload`) call `resolveActiveGarage()` / `accessToLocation(userId, garageId)` and check a key themselves.
- **Creating a garage always goes through `createBusiness()`** (`create.ts`: business, roles, first location and Owner membership in one transaction), used by registration, the admin invite and the seeds. `backfillOrganisations()` (`backfill.ts`) upgrades existing garages; run `--verify` after.
- **Messaging with several staff**: a message records `fromGarage` when written; unread/read rules use it (`messaging.ts`), so one colleague opening a thread never marks another colleague's reply as read for the customer. Threads are reachable by anyone who can open the thread's *location* with `messages.view`/`messages.reply`.
- **Billing belongs to the business** (`billing.ts`): `Organisation` is the source of truth for plan, subscription, lead credits, Stripe Connect account and the invoice counter, and every billing write goes there first (`updateBilling`/`writeBilling`/`addCredits`/`takeCredit`/`claimStripeId`/`nextInvoiceCounter`), then is mirrored onto the locations' Garage columns (`mirrorBillingToLocations`, never throws). `stripeCustomerId`/`stripeSubscriptionId`/`stripeAccountId` are unique on Garage, so only the oldest location carries them. **Decide from `getBilling(garageId)`, never from `garage.plan` / `garage.leadCredits`** (those are display copies). Credits and the monthly lead allowance are one pool across locations (`locationIdsOf`); invoice numbers are one sequence per business; Connect is one account per business. A garage with no business still uses its own columns. In tests set billing with `setBilling(garageId, patch)` from `src/test/fixtures.ts`, not `prisma.garage.update`. `syncOrganisationBilling` (garage -> business, single location only) survives only as the `--sync-billing` repair.
- **Staff and roles** (flag `staff`): `roles-service.ts`, `staff-service.ts`, `invites.ts`, `rules.ts` (pure). Rules: nobody grants more than they hold, nobody edits their own access, the last Owner can't be removed/demoted/suspended, only an Owner assigns Owner (and only at all locations), a role in use can't be deleted. Invites are single-use sha-256-hashed tokens (7 days) accepted at `/join/[token]`; an existing customer account is converted to `GARAGE` (reverted when removed from its last business; never ADMIN/SUPER_ADMIN or suspended). Every change is audited with `organisationId`; the business sees its own trail at `/garage-dashboard/activity`.
- **Locations** (flag `locations`): `locations-service.ts`. A new location starts `PENDING` (admin approves with the usual readiness check); closing one **archives** it (`ARCHIVED`: read-only, off the marketplace, history kept; never deleted; refused for the only working location, one with upcoming bookings, or one the platform suspended). `location-status.ts` is the one place that decides read-only (`readOnlyReason`): writes are allowed only for PENDING/APPROVED, so a new status fails closed. Public code requires `status === "APPROVED"` exactly. The active location defaults to a non-archived one (`pickActiveLocation`).
- **One lead per business** (`lead-routing.ts`): `pickLocation` (postcode district, area prefix, city, rating, id) chooses the location that handles a job request; push matching, the portal pull, and the respond route all dedupe through it, and the earliest answer wins a race (`wonTheLead`), refunding the loser's credit.
- **Own jobs only** (`own-jobs.ts`): `bookings.view` shows the whole location, `bookings.viewOwn` only bookings assigned to the technician linked to the caller's login (`Technician.userId`, unique per location). `jobScope(ctx, area)` + `scopeWhere(scope)` filter bookings/diary/overview/nav badges; an own-jobs caller may only start, complete or no-show their jobs and add notes (`disallowedOwnJobFields`), and a login with no link sees nothing. Managers link logins in Settings > Technicians (`technician-link.ts`: only people who work at the location). The dashboard returns `sees.*` flags and zero money unless `insights.view`.
- **Notifications and push** (`notify-access.ts`): each notification type needs a permission (`NOTIFICATION_PERMISSION`); the bell lists only the types the role may see, and push goes to the devices of members who can open the location *and* hold the permission (subscriptions are keyed by the person, so removal/suspension stops them at once; old location-keyed subscriptions still work).
- **CSRF** (`src/lib/origin.ts`, enforced in `proxy.ts` for every `/api` write except `/api/auth/*`): a write must come from our own origin (`Origin` header, else `Sec-Fetch-Site`); requests with neither (webhooks, cron, curl) pass. This is what stops a sibling subdomain (garage sites) riding the session cookie.
- **Feature flags** (`features.ts`): `ORG_FEATURES=staff,locations,sites` (or `all`) and optional `ORG_BETA_IDS`. In production nothing is on unless set; elsewhere everything is on. The portal hides Team/Roles/Business/Activity/Locations while their flag is off and routes answer 404 `FEATURE_OFF`.
- **Portal UI**: `PortalShell` takes `access` (permission keys + features), `locations` and `activeLocationId` from the layout. `filterNav`/`isPageAllowed` (`nav-filter.ts`) hide and redirect away from pages the role can't open; `useCan()`/`<Can>` (`access-context.tsx`) hide controls; `LocationSwitcher` appears for businesses with several locations (`POST /api/garage/location` sets the `qmg_loc` cookie; the page remounts keyed by location and `use-api` sends `x-qmg-location`). **Hiding is only a courtesy: every API route checks again** (and `src/lib/org/architecture.test.ts` fails if a new `withGarage` route is missing from its snapshot).
### Hardening conventions (phase 4)

- **Authorising a request.** Every `/api/admin/*` handler starts with `const auth = await requireAdmin()` (`src/lib/admin-auth.ts`; `{ superOnly: true }` for platform settings and garage invites, which `architecture.test.ts` pins to exactly those two routes). Customer-facing routes use `requireSession()` (`src/lib/session.ts`). Both answer 401 and never let a session without a string user id through. A new admin route without `requireAdmin` fails the architecture test.
- **No `any` in production code** (ESLint error; tests may cast mocks). A caught value is `unknown`: use `errorCode(err)` (Prisma `P2002`/`P2003`...), `errorMessage(err)` and `isAbortError(err)` from `src/lib/errors.ts`. The session user is typed in `src/types/next-auth.d.ts`.
- **Rate limits** (`src/lib/rate-limit.ts`, database-backed): `limitByIp` on public reads and token links (`/api/garages` 120/min, widget config and slots 120/min, booking-manage slots 120/min, job tracking 120/min, guest accept 20 per 10 min), `limitByKey` per signed-in user on writes that email someone (messages 60/min, quotes 60 and bookings 30 and reviews 20 per 10 min). Loopback and unknown IPs are skipped, so tests don't throttle themselves. `app/api/rate-limits.test.ts` checks the wiring.
- **Images**: `<RemoteImage>` (`src/components/ui/remote-image.tsx`) uses `next/image` only for hosts listed in `next.config.js` (`IMAGE_HOSTS`, passed to the app as `NEXT_PUBLIC_IMAGE_HOSTS`, includes `*.public.blob.vercel-storage.com`) and falls back to a plain lazy `<img>` for any other URL, because `next/image` throws on an unlisted host. Add a host in that one list.
- **Logging and health**: `src/lib/log.ts` writes one JSON line per event and masks emails and phone numbers; the mail and SMS dev fallbacks no longer log bodies in production. `GET /api/health` is 200 or 503 and says nothing about why (it goes to the log). `app/global-error.tsx` is the last-resort page.
- **Indexes** added in both schema files (additive `CREATE INDEX` only). **Schema changes must stay additive**: `npm run schema:safety [baseRef]` (also a CI job on pull requests) refuses `DROP TABLE/COLUMN`, `TRUNCATE`, `DELETE` and column type changes against the base branch's `schema.prod.prisma`.
- **SEO**: every top-level page has a title and indexing rule (client pages carry them in a sibling `layout.tsx`; `architecture.test.ts` checks); an unknown or unapproved `/garage/<id>` is a real 404.
- **Dependencies**: `next` is pinned exactly and was raised to 16.4.2 for security advisories (RCE in `next/og`, SSRF in image optimisation, cache poisoning); CI runs `npm audit --omit=dev --audit-level=high`. Dependabot groups weekly patch/minor updates and ignores majors of next, react and prisma. CodeQL runs on pushes, pull requests and weekly.
- Not built yet: a nonce-based Content-Security-Policy (Report-Only first: Stripe, Google and Next's own inline scripts need testing), `@vitest/coverage-v8` thresholds, and structured logging beyond mail/SMS/health.

### Business websites on subdomains (flag `sites`)

Each business can publish a one-page website at `<name>.<NEXT_PUBLIC_ROOT_DOMAIN>` (logo, colours, About text, services, every location with live hours, reviews, FAQ, contact). **Off unless `NEXT_PUBLIC_ROOT_DOMAIN` is set** (it is read at build time) and the `sites` flag is on for the business. Locally: `$env:NEXT_PUBLIC_ROOT_DOMAIN="localhost"; npm run dev`, then open `http://<name>.localhost:3000`.

- **Host routing is `proxy.ts` + `src/lib/org/host.ts`** (pure, tested; `proxy.ts` itself isn't in vitest's include, `proxy-tenant.test.ts` drives it directly). `classifyHost` decides tenant vs marketplace (one label deep, reserved/malformed labels and look-alike suffixes are the marketplace). On a tenant host `/`, `/opengraph-image`, `/sitemap.xml`, `/robots.txt` are *rewritten* to `/sites/<label>[...]`; `/favicon.ico` answers 204; static assets pass; **everything else goes to the marketplace with a 308** (target built from `NEXT_PUBLIC_APP_URL`, never from the request host). The proxy can't send that redirect itself: Next turns a `Location` on the host it believes the request was for into a relative one, which in local dev and `next start` is the marketplace's own origin, so the browser looped on the business's address. The proxy therefore rewrites to `app/sites/-/main-site/route.ts`, which answers the 308 (target in the proxy-set `x-qmg-apex` header, re-checked against the configured main site); `/api/*` and `/sites/*` are 404. `/sites/:path*` is in the proxy matcher on purpose: the generic pattern skips any path with a dot, which let `/sites/<label>/sitemap.xml` bypass the proxy. On the marketplace `/sites/*` is 404 and **any inbound `x-qmg-site` header is a 400** (the proxy alone sets it, so one that arrives is forged). Never set a cookie `Domain`: sibling subdomains are same-site, so a host-only cookie is what keeps sessions off business sites (`architecture.test.ts` scans for it).
- **Lean render path**: `app/layout.tsx` checks `x-qmg-site` and renders a bare `<html><body>` (no providers, i18n, compare bar or service worker); `app/not-found.tsx` does the same (the marketplace header needs a session provider). `app/sites/[label]/*` handlers must be `export const dynamic = "force-dynamic"` (a handler that never reads the request is built static and cached forever; the architecture test checks).
- **Data and caching** (`src/lib/site/*`): `OrganisationSite` (+ `SiteDomain`, `SiteRevision`) holds the published `theme`/`content` and a separate `draftTheme`/`draftContent` with an optimistic `version` (a stale save gets 409 `STALE`). `loadPublicSite` shows only what visitors may see (and nothing at all when the `sites` flag is off for the business: that is the rollback, content kept) and is cached 60 s with `unstable_cache` under tag `site-label:<label>`; **`invalidateSite`/`invalidateSiteForGarage` (`cache.ts`) must be called by anything that changes what a site shows** (publish, take offline, admin action, a location's profile/hours/status) and uses `{ expire: 0 }`, because the default `"max"` serves the stale copy to the next visitor, i.e. the owner right after publishing.
- **Workflow** (`site-service.ts`, admin side `site-admin.ts`): DRAFT -> `requestPublish` -> PENDING_REVIEW -> admin approves at `/admin/sites` -> PUBLISHED; after the first approval the owner publishes edits and takes the site offline/online by themselves (`UNPUBLISHED` <-> `PUBLISHED`, no re-review), the last 20 published versions can be restored, and an admin can switch any site off (`disabledAt`, reason shown to the owner). A site needs at least one APPROVED location. Addresses (`SiteDomain` rows) are never deleted: changing the address turns the old one into `REDIRECT` (max 5, 308 to the current one); `parseLabel`/`subdomainProblem` (`org/subdomain.ts`) enforce 3-40 ASCII chars, a reserved list, no `xn--`.
- **Content is data, never markup**: plain text rendered as React text nodes; About uses the Markdown subset in `articles.ts` (`safeHref` accepts only `https:` or a root-relative path); images must be Blob URLs under `orgs/<orgId>/` (`isOwnOrgImageUrl`), uploaded through `app/api/garage/site/upload` (sniffed JPEG/PNG/WebP, 2 MB). Colours are validated hex; `deriveTheme` picks pure black/white text so every pairing is at least 4.5:1 (property-tested over thousands of colours).
- **SEO**: the site is self-canonical with its own sitemap/robots/share image; the marketplace `/garage/[slug]` page stays canonical for transactions. JSON-LD is one `Organization` + an `AutoRepair` per location (`branchOf`), no self-awarded `aggregateRating`. Calls to action link to the marketplace (`/widget/<slug>`, `/garage/<slug>`): a business site has no write endpoints of its own.
- **Basic and advanced ("Website Pro")**: every business gets the basic site: banner photo with a dark/darker/brand-colour layer (`hero.overlay`, deliberately no "none": text on a photo can't be contrast-checked), alignment, ready-made style presets (`presets.ts`), a real trust line (marketplace rating, review count, verification: `PublicSite.trust`, never typed in), phone-first header/contact band and a mobile call/book bar. The advanced options live together in `content.pro` (split banner layout, height, photo focus, About and contact photos, notice bar, hide credit line) and belong to the **Premium plan** (`websitePro` in `portal/plans.ts`, price from `PLANS`; free for everyone while `PLANS_ENFORCED` is off). `tier.ts` decides: `siteTier(org)`, `contentForTier` (visitors and previews see defaults for `pro` without the plan), `mergeSavedContent` (a save without the plan keeps the stored `pro`, so it returns on upgrade). The builder shows the comparison card (`ProPanel`) and locks the controls (`ProGate`, a disabled fieldset); the server enforces it regardless. "Own domain name" is listed as coming soon only.
- **Cache versioning**: the site cache outlives a deploy, so `SITE_CACHE_VERSION` (`public-cached.ts`) is part of every key. Raise it when `PublicSite` or the content shape changes (`cache-version.test.ts` pins the content shape). Skipping it crashed the page on stale entries without `pro`/`trust`.
- **Previews**: `/site-preview` (owner, needs `website.edit` + the flag) and `/site-preview/<siteId>` (admin) render the saved *draft* through the same `SiteRenderer`, noindex, with a banner. Portal pages: `/garage-dashboard/site` (builder), `/admin/sites` (queue, preview, switch off/on).
- Adding a route under `app/api/garage/site/**` means adding it to the permission snapshot in `architecture.test.ts` (`website.edit`).

### Two parallel request flows

1. **Authenticated quote flow**: a logged-in OWNER picks a vehicle + garage and requests a `Quote` (`app/api/quotes/route.ts`), which a garage can turn into a `Booking`.
2. **Guest job-request flow** (no login required): a visitor posts a `JobRequest` (`app/api/job-requests/route.ts`) with guest contact info; the request gets a random `token` (crypto.randomBytes) used to build a guestaccessible tracking URL at `/post-job/track/[token]`. `src/lib/job-matching.ts` matches the request to nearby garages by city/postcode prefix + `serviceType` membership in the garage's services list, and emails matched garages (`sendMail`) plus a confirmation to the guest. Garages respond with a `JobResponse`; the guest accepts one via `app/api/job-requests/track/[token]/accept/route.ts`, which becomes a `Booking`.

Keep these two flows (`Quote`/`Booking` vs `JobRequest`/`JobResponse`) distinct — they are separate Prisma models with separate routes and are not interchangeable, even though both end in a `Booking`.

### Garage portal (`/garage-dashboard/*`) and booking widget

Garages use a multi-page portal: Dashboard, Diary, Bookings, Reviews, Profile, Website, Pricing, Enquiries, plus Insights and Settings. `app/garage-dashboard/layout.tsx` provides the sidebar shell (no marketing Header/Footer); pages live in `app/garage-dashboard/*` and their UI in `src/components/garage-portal/*`. The old `/garage-dashboard?booking=ID` / `?quote=ID` notification links are redirected by the portal root page (`legacyGarageRedirect`).

- **API**: all garage endpoints are `app/api/garage/*`, wrapped in `withGarage()` (`src/lib/garage-auth.ts`). It re-checks the DB on every call (the JWT role can be stale), enforces the route's permission at the active location, gives suspended locations read-only access (`{ write: true }` routes 403), and maps `BookingError`/zod errors to JSON. `GET /api/garage/me` also returns the business, the caller's locations and permission keys (for hiding navigation; never trust it for security). Middleware does not protect `/api/*`.
- **Uploads** (`/api/upload`, `/api/garage/documents`) sniff the real file type from the bytes (`src/lib/image-sniff.ts`), never trust `file.type`/`file.name`, rate-limit per garage (`limitByKey`), and delete replaced files. `Garage.logo` may only point at the garage's own storage folder.
- **One booking service** (`src/lib/portal/booking-service.ts`): `createBooking`, `transitionBooking` (rules in `booking-status.ts`), `rescheduleBooking`, `findOverlaps`, `acceptJobResponse`. Every booking path (owner, garage, widget, guest job accept) goes through it. Don't write `prisma.booking.create` elsewhere.
- **Walk-in/widget customers have no account**: `Booking.ownerId`/`vehicleId` are nullable; the portal reads only the snapshot columns (`customerName`, `vrm`, `vehicleMake`…), never joins owner/vehicle. Invariant: `ownerId != null ⇒ vehicleId != null`. `onDelete: Restrict` on both is deliberate.
- **Sources**: `Booking.source` ∈ MARKETPLACE | QUOTE | JOB_REQUEST | WIDGET | DIRECT. KPI definitions (created/attended/FIV/no-show) are documented at the top of `src/lib/portal/kpi.ts`.
- **Times are Europe/London**: use `src/lib/portal/tz.ts` (civil `YYYY-MM-DD` dates → half-open UTC ranges). Never `setHours` or `T23:59:59Z`.
- **Search is cross-DB**: SQLite's client has no `mode: "insensitive"`, so bookings store a lower-cased `searchText` and a normalised `vrm`.
- **Public widget** (`/widget/[slug]`, `/api/widget/[slug]/*`): no auth; 404 unless the garage is APPROVED and `portalSettings.widget.enabled`. Abuse limits are counted from the `Booking` table (per email, per hashed IP, per garage per hour), plus a honeypot. `next.config.js` allows framing for `/widget/*` only; everything else is `SAMEORIGIN`.
- **No double-booking**: customer-facing/capacity-respecting creation passes `checkAvailability: true` to `createBooking`, which re-checks the slot inside the transaction under a per-garage row lock (`lockGarage`); reschedules do the same. Bookings with only a placeholder time (`timeConfirmed = false`) don't hold capacity.
- Client IP for the widget's per-IP limit comes from `clientIp()` (`ip-hash.ts`): Vercel's header, else `X-Forwarded-For` honouring `TRUSTED_PROXY_HOPS`. On Vercel this isn't needed (it uses `x-vercel-forwarded-for`); behind any other proxy set that env var or the limit is spoofable.
- Garage-facing emails respect the toggles in Settings via `emailGarage()`.
- Demo data: `npx tsx prisma/seed-garage-portal.ts` (delete-and-recreate; login `premier@quotemygarage.dev` / `garage123`).

### Admin portal (`/admin/*`) and customer portal (`/dashboard/*`)

All three roles share one shell, `src/components/portal-shell/` (`PortalShell`, `Sidebar`, `Topbar`, nav definitions in `nav.ts`). Layouts pass a portal id (`garage | admin | owner`) because nav objects hold icon functions and can't cross the server/client boundary; sidebar "needs attention" badges come from `src/lib/portal/nav-badges.ts`. Garage-portal keyboard shortcuts (`g` then a letter, `/`, `?`) are declared per nav item.

- **Tables are responsive by construction**: use `DataTable` (`src/components/ui/data-table.tsx`). Below `md` each row becomes a card (columns declare `mobile: title | badge | detail | actions | hidden`), sorting becomes a select, and rows can be selectable for bulk actions. Don't hand-roll `<table>` for lists.
- Admin lists use `ResourceList` (tabs + search + pagination in the URL). Admin APIs page in the database when there is no text search; search stays in memory because SQLite and Postgres disagree on case-insensitive `contains`.
- Garage approval checks `garageReadiness()` (`readiness.ts`); approving an incomplete profile needs `force: true`. Garages are notified of status changes. The Garages list shows each row's business and whether it is a branch added later ("New location of …"); archived locations have their own tab and can't be approved/suspended by an admin. The Support lookup finds staff through their business and shows their roles and the activity at the locations they can open.
- `/admin/widgets` flags repeat widget visitors (same hashed IP / email 3+ times in 24h).
- Customers: `/dashboard/{bookings,quotes,vehicles,messages,reviews,settings}`. Account APIs: `/api/account`, `/api/account/change-password` (shared logic in `src/lib/change-password.ts`).

### Customer manage link, reminders and audit trail

Every booking gets a `manageToken` (128-bit). Emails link to `/booking/[token]`, a public page (noindex, no-referrer) backed by `/api/booking/[token]`: view, cancel (`transitionBooking` with `actor: { role: "OWNER", viaToken: true }`) and review (`review-service.ts`, which also serves signed-in customers; `Review.ownerId` is nullable). `GET /api/cron/booking-reminders` (CRON_SECRET) sends appointment reminders once each (`reminderSentAt` claim). `BookingEvent` is an append-only history written by the booking service and shown as the drawer timeline; the job sheet prints at `/garage-dashboard/bookings/[id]/job-sheet`.

### Online deposits (Stripe)

Garages can take a deposit on widget bookings (`portalSettings.payments`: enabled, depositPercent, refundPolicy). Flow: widget POST creates the booking, then `createDepositCheckout()` (`payment-service.ts`) returns a Stripe Checkout URL and marks `paymentStatus = PENDING`; `POST /api/stripe/webhook` (signature-verified over the raw body, idempotent via `StripeEvent`) marks it PAID or, on expiry, cancels the unpaid booking so the slot is released. Cancelling any booking goes through `transitionBooking`, which calls `refundOnCancel()` (pure rules in `payments.ts`: a garage or system cancel refunds in full; a customer cancel follows the garage's policy). Refund failures never block a cancel; they are written to the booking history for manual follow-up. With no `STRIPE_SECRET_KEY` the feature is off and booking works as before. **Payouts use Stripe Connect (Express, destination charges).** A garage connects its own account from the Website page (`POST /api/garage/stripe/connect` → Stripe-hosted onboarding; `GET` re-reads the account, and `account.updated` webhooks keep `Garage.stripeChargesEnabled` current). Deposits can only be switched on once that is true, and the charge is made with `transfer_data.destination` so the money goes straight to the garage, minus an optional platform fee (`PLATFORM_FEE_PERCENT`, 0–30, default 0; `platformFeePence()`). Refunds use `reverse_transfer` + `refund_application_fee` to claw the money back from the garage. The webhook route accepts two secrets: `STRIPE_WEBHOOK_SECRET` (platform events) and `STRIPE_CONNECT_WEBHOOK_SECRET` (connected-account events).

### Garage tools: customers, invoices, diary

- **Customers** (`/garage-dashboard/customers`) are derived from bookings, not stored: `buildCustomers()` (`customers.ts`, pure) groups by email, else phone, else registration (`customerKey`, e.g. `e:ann@example.com`); `customers-db.ts` loads the rows. The only stored data is `CustomerNote` (a private per-garage note keyed by that same key). A garage can merge duplicates ("Same person?" in the customer drawer): `CustomerMerge` stores a fromKey → toKey redirect that `buildCustomers()` applies (`resolveKey` follows chains and can't loop; the merged-into identity's name/contact win; the private note moves across). A merge can be split again.
- **Invoices**: `GET/POST /api/garage/bookings/[id]/invoice` (download / email the PDF, made with `pdf-lib` in `invoice.ts`). A completed booking gets `INV-0001`-style numbers from the business's invoice counter (`nextInvoiceCounter`, one sequence across its locations) the first time an invoice is generated and keeps it; `@@unique([garageId, invoiceNumber])` guarantees no duplicates per location and the shared counter makes numbers unique across the business. Total = `finalInvoiceValue ?? totalPrice`, minus a deposit still held. The standard PDF fonts are Latin-1 only; `pdfSafe()` replaces other characters with "?" rather than throwing.
- **Diary**: week / day / month views. Month (`MonthGrid`) is always six Monday-first weeks (`monthGrid()`), which is exactly the diary API's 42-day limit. Dragging a booking (HTML5 drag and drop, no library) proposes a move that the garage must confirm; the move is an ordinary `PATCH /api/garage/bookings/[id]` so overlap, past-time and notification rules all still apply, and an overlap offers "Move anyway". Dropping keeps London wall-clock time (`sameTimeOnDay`). Keyboard: focus a booking and press Alt+arrows (±1 day, ±30 min; ±7 days in month view) — same confirmation (`keyboardMove`/`shiftSlot`). Touch devices can't drag; they tap a booking and use the drawer's Reschedule panel. In Playwright use `dragWithMouse` (`e2e/helpers.ts`): `dragTo()` doesn't start a native drag.

### Text messages (SMS)

`src/lib/sms.ts` posts to Twilio's REST API (no SDK); with no credentials it logs and reports `skipped` like `mail.ts`. `notifyCustomerSms(bookingId, kind)` (`sms-notify.ts`) is the only sender and applies every rule: the customer opted in (`Booking.smsOptIn`, or `User.smsOptIn` for account holders), the garage switched texting on (`notifications.smsCustomer`, off by default because SMS is billed), a UK mobile (`toE164Mobile`), reminders not sent 21:00–08:00 London, and a cap of `MAX_SMS_PER_BOOKING`. It never throws and writes each send/failure to the booking history. Triggers: garage confirm / cancel / reschedule in `booking-service.ts`, and `sendDueSmsReminders` in the `/api/cron/booking-reminders` job (daily on Vercel Hobby; reminders cover everything up to the end of tomorrow, London, see `reminderHorizon`) (its own `smsReminderSentAt` claim, released on quiet hours or failure). Consent is captured on the widget form (only when the garage has texting on), in the garage's New booking dialog, and in the customer's account settings. Replying STOP is handled by the carrier/Twilio.

### Rate limiting, audit log and accessibility

- `src/lib/rate-limit.ts`: DB-backed (`RateLimitHit`, no in-memory state, so it holds across instances). `limitByIp(req.headers, name, limit, windowMs)` returns a ready 429 or null; unknown and loopback IPs are skipped. Applied to sign-in, register, forgot/reset password, public job requests and manage-link POSTs. Behind a proxy set `TRUSTED_PROXY_HOPS` or per-IP limits are spoofable (see above).
- `src/lib/audit.ts`: `audit(session, { action, targetType, targetId, detail })` after every admin mutation (never throws). Browse at `/admin/audit`.
- Accessibility is tested: `e2e/a11y.spec.ts` runs axe (WCAG 2.1 A/AA) on the main pages at desktop and phone size. Rules of thumb: text colours need 4.5:1 (use `text-slate-500` not `-400` on white; `#C2410C` for orange text on light backgrounds, dark text on orange buttons), icon-only buttons need `aria-label`, list filters use `FilterTabs` (not ARIA tabs), full-page forms need a `main` landmark.
- CI (`.github/workflows/ci.yml`): `build` (lint, vitest, build), `e2e` (seeded SQLite + Playwright), and `postgres` (same vitest suite against Postgres with `schema.prod.prisma`; non-blocking until first seen green).

### SEO

Public garage pages emit real metadata, canonical URL and `AutoRepair` JSON-LD (`src/lib/seo.ts`); `app/sitemap.ts` and `app/robots.ts` list approved garages and block portals/APIs. All portals, the widget and token pages send `noindex`.

### Mail has a dev fallback

`src/lib/mail.ts` lazily builds a nodemailer transporter from `EMAIL_SERVER_*` env vars; if they're unset (e.g. local dev without SES configured), `sendMail` no-ops and just logs `[mail:dev-fallback]` instead of throwing. Don't assume missing email env vars is a bug — it's the expected local-dev state.

### Compare feature is client-only state

`src/context/CompareContext.tsx` keeps the "compare garages" selection (max `MAX_COMPARE_GARAGES`, see `src/lib/constants.ts`) in React state hydrated from/persisted to `sessionStorage` (key `COMPARE_STORAGE_KEY`) — no server/DB persistence.

## Phase 3 (growth and monetisation)

- **Plans** (`src/lib/portal/plans.ts`, `billing-service.ts`): the single place for plan names, prices, monthly lead limits and feature gates. Nothing is enforced until `PLANS_ENFORCED=true` (`hasFeature`, `leadDecision` are no-ops before that). Gates: insights API, SMS (`notifyCustomerSms`), online deposits (`createDepositCheckout`), and the monthly lead allowance in `POST /api/job-requests/[id]/respond`, past which a lead costs a credit (`spendLeadCredit`, refunded if the save fails). Subscriptions, credit packs and featured placement are charged to the **platform** Stripe account (not Connect). `handleStripeEvent` hands every verified event to `handleBillingEvent` after the idempotency check; deposit sessions and billing sessions never interfere because billing sessions carry `metadata.kind`. Credit grants are idempotent on `LeadCreditTransaction.stripeSessionId`.
- **Search ranking** (`src/lib/ranking.ts`, `GET /api/garages`): default sort is `best`, scored in memory over up to 500 matches (rating via Bayesian average, response time, completion rate, distance when `lat`/`lng` are given, price for the searched service, verified). Featured garages are pinned first, capped at 3 so payment can't fill the page, and labelled "Featured". Garage response time is a running average updated when a job response is created (`avgResponseMins`, `responseSamples`). Price guidance (`src/lib/price-guidance.ts`) is the interquartile range of accepted quotes and shows only with 5+ samples.
- **Messaging**: a message is unread until someone other than its sender opens the thread (`GET /api/messages` marks read, except for admins). `src/lib/messaging.ts` has the counts and `threadSummaries`; the sidebar badge key is `unreadMessages`. Emails go only for the first unread message of a burst (`isFirstUnreadFromSender`) and respect `notifications.emailMessage` for garages.
- **Installable app / push**: `app/manifest.ts`, icons drawn at `/icons/[size]`, `public/sw.js` (offline page + push only; it deliberately caches no pages or API data), registered only in production by `RegisterServiceWorker`. `notifyUser`/`notifyGarage` also call `pushToUser`/`pushToGarage` (`src/lib/push.ts`; no-op without VAPID keys, never throws, deletes 404/410 subscriptions). A garage account's subscriptions belong to the garage, not the login.
- **DVSA MOT history** (`src/lib/mot-history.ts`, `GET /api/vehicle-lookup`): public, per-IP rate limited. The endpoint path and response shape were written from DVSA's published docs without a live key: confirm against a real response (`DVSA_MOT_BASE_URL` overrides the path). Credentials come from `getSetting()` (`src/lib/platform-settings.ts`): a value a super admin saved at `/admin/settings` (AES-256-GCM in the `PlatformSetting` table, key `SETTINGS_ENCRYPTION_KEY` or `NEXTAUTH_SECRET`; write-only, never returned, never audited) beats the env var; reads never throw, so a missing table or an undecryptable value falls back to env. The page's "Test DVSA connection" reports whether the token and the API key are accepted. `motHistoryConfigured()` / `dvlaConfigured()` are **async**.
- **Moderation and verification**: a garage can dispute a review once (`POST /api/garage/reviews/[id]/dispute`); admins decide at `/admin/reviews` (Disputed tab; `PATCH /api/admin/reviews`). Verification documents are **private** blobs streamed only through the garage and admin file routes. `/admin/support` is read-only and every account opened is audited (`SUPPORT_VIEW`).
- **Guides and blog**: `Article` rows, written at `/admin/articles`, public at `/blog` and `/blog/[slug]` (drafts 404). Bodies are a Markdown subset parsed into data and rendered as React elements (`src/lib/articles.ts`), so author text never becomes raw HTML; only http(s), site-relative and mailto links survive.
